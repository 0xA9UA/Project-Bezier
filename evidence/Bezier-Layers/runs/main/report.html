CPU-selected sphere layers

The proposed engine works: the CPU selects a content-associated z band, the GPU chooses and executes experts within it, then the CPU can select a different band from the updated state. All expert matrices and the full hidden state remain on GPU. The CPU stores the layer catalogue and a small learned controller.

The trained adaptive model averaged 95.46% digit accuracy. It switched layers within 6.20% of predictions. CPU control was faster than GPU hierarchical control in 1 of nine median timing settings, but beat the fastest tested single-device implementation in 0 of nine. These timings have visible desktop variability and are not proof of universal speed ordering.

What changes during a prediction

GPU activation → eight-float summary → CPU layer ID → GPU Bézier route and expert matrix products → updated activation → repeat.

Example test item 72: true digit 4, predicted digit 4, layer sequence 3 → 2 → 2 → 2. The assigned family changes from digits 6/7 to digits 4/5 in this example. The plots show actual saved cubic paths; example selection takes the first six test inputs exhibiting a switch and is illustrative, not an unbiased sample of routes.

The layer IDs are logical addresses. Five digit families are explicitly assigned to five bands, with four experts per band. The CPU makes a hard layer choice; GPU uses two weighted experts inside that band. The eight-float summary is learned on GPU. The full hidden vector, matrix multiplication, SiLU, normalization and fine routing stay on GPU. The illustrated final exit joins the last interior position to the sphere surface; it adds no final learned processing step.

Learning and switching

Six models: adaptive and entry-only layer selection, seeds 7/19/42, 80 epochs, the same initial weights and minibatch orders. Classification loss plus 0.5 times mean family-routing loss trains the model. Families are digit//2; labels are available only for training and evaluation, never for inference decisions. The hard layer argmax has no classification gradient; its auxiliary supervised loss trains the controller. This tests deliberately assigned specialization, not discovered categories in a pretrained language model.

Adding +4/-4 to two hidden-state components after the first update changed 7.81% of later layer decisions on average in the trained adaptive models. All frozen-layer controls kept their layer sequence. Smaller interventions and their accuracy effects are retained in diagnostics.json. This is evidence of feedback-dependent decisions, not proof that perturbations help.

Forcing every step into layer zero reduced adaptive accuracy to 55.00%. This intervention establishes dependence on layer choice, not superiority over a separately trained baseline.

It is not an independently optimized flat MoE model.

Hierarchical search reduces fine expert scores per hop from 20 to 4 for digits, 512 to 16 for matrix_heavy, and 8,192 to 128 for many_experts. Both CPU and GPU layer controllers get this saving. It does not reduce the selected expert matrix work below the same two experts per hop, and it does not compress the weight bank.

Communication and decision frequency

The CPU layer controller receives 32 bytes of state summary and sends an eight-byte layer ID per input per decision. Four decisions plus input/output handling give 5 CPU-to-GPU and 5 GPU-to-CPU copies, with 456 logical payload bytes for a single digit input. The GPU-only engine has two boundary copies. Small messages still require the CPU to wait for the GPU-produced summary before deciding the next layer. Pinned buffers protect lifetimes and CPU reads; they do not remove that dependency.

Reconsidering less often is a post-training approximation. At interval four the layer stays fixed throughout the four-hop input, so it does not implement adaptive switching during that run. It must not be counted as an equal-quality dynamic-router speedup without its quality results.

The small model stores 485 serialized bytes of catalogue metadata. CPU control moves 180 bytes of controller parameters to system RAM; 0.343 MiB of model parameters remain on GPU. Coordinates and radii are cached on the execution device for fine routing. Metadata in RAM does not move the expert weights out of VRAM, shrink total model storage, or automatically organize arbitrary existing weights into semantic groups.

Runtime refinement and limits

The initial uncached pass exposed avoidable coordinate recomputation. The refined engine caches fixed expert coordinates and layer radii equally for all schedules. Cached/uncached outputs, IDs, paths and cache invalidation are tested. Original timings and source snapshots remain available; the refinement is exploratory and does not change trained weights or category assignments. Geometry caches are bypassed during gradient-enabled training and cleared by train() or load_model_state(). Manual parameter edits require clear_inference_cache().

This is a synchronous eager PyTorch runtime on one desktop CPU/GPU, without fused kernels, CUDA-graph replay, request pipelining, expert paging, or reinforcement-learning evaluation. Training can run with CPU controller gradients through differentiable summary copies, but runtime timing here concerns inference. The positive result is an implemented and verified layer-switching mechanism with a smaller fine-search space. A dependable speed or final-accuracy advantage for CPU placement has not been established.
